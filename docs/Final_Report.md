## 1. Problem Statement

From the brief (`Full_Approach_Design_Document.docx.pdf`, "The Problem"):

> Think of this project as building the brain of a security guard for face-based login. The guard has two jobs. First, when someone signs up (registration), take a clear photo of their face and remember it. Second, when someone tries to log in later (verification), look at their face again and answer two questions: is this a real, live person in front of the camera right now, and does this face actually belong to the person who signed up.

A face-matching system alone can be fooled by a printed photo, a video, or a photo on a phone screen. The system therefore needs two additional capabilities beyond matching: **liveness detection** (is this a real, live person) and **image quality assessment** (is the captured photo even usable in the first place). The brief splits this into two phases — registration and verification — which this project's design merges into one shared pipeline with two entry points, since both phases reuse the same quality, liveness, and matching logic.

## 2. Approach & Architecture

Full pipeline diagram: **[`docs/architecture_diagram.png`](architecture_diagram.png)** (editable source: `docs/architecture_diagram.svg`, generated by `scratch/build_architecture_diagram.py`).

**Shared pipeline** (both registration and verification): Capture Input (WebRTC webcam frame) → Face Detection (MediaPipe BlazeFace, reject 0 or >1 face) → Quality Assessment (7-check weighted composite score, see Section 3.3) → Liveness Detection (Passive: MiniFASNet via DeepFace; Active: randomly-selected blink or head-turn challenge) → Face Embedding (ArcFace via DeepFace, pretrained, no fine-tuning).

**The fork**, after embedding:
- **Registration**: Consent gate (refuses without explicit consent) → Duplicate check (cosine similarity vs. every existing front template, threshold 0.68) → Store template (Fernet AES-128 encrypted at rest, front-only — see Section 4's Multi-Angle scope decision).
- **Verification**: Fetch all active users' stored front templates → 1-to-N cosine-similarity match, accept best score ≥ 0.40 (frontal-vs-frontal calibrated, Section 3.1) → Accept/Reject, logged to `verification_logs`.

**Deployment**: three local components, one machine, no cloud dependency — Streamlit UI (+ `streamlit-webrtc` for the camera feed) → FastAPI backend (`/register`, `/verify`) → SQLite (local file, `users`/`templates`/`access_log`/`verification_logs`). API key auth and a sliding-window rate limiter sit in front of the backend.

**Deliberate deviation from the brief's original three-angle design**: registration originally captured front/left/right templates via a pose-gated head-turn challenge. That flow was simplified to front-only capture — see Section 4 for the full rationale and evidence.

## 3. Results (real measured numbers only)

### 3.1 Face Matching Accuracy (Frontal-vs-Frontal — the production verification path)
Source: `data/Evaluation_Report.md` Section 3.
- **Equal Error Rate (EER):** 3.19% at EER-optimal threshold 0.2642
- **ROC AUC:** 0.9953
- At the **deployed threshold of 0.40**: **FAR 0.34%** (2/595), **FRR 15.09%** (16/106), **HTER 7.72%**
- Rationale: the EER-optimal threshold's 3.19% FAR was judged too high for a security-critical system; 0.40 was chosen deliberately to force near-zero false acceptance, accepting a higher false-rejection rate as the tradeoff (users are re-prompted automatically within milliseconds on a false reject, at negligible cost; a false accept is a real security failure).

### 3.2 Passive Liveness / Attack Detection (re-measured this pass on a larger sample)
Source: `data/Evaluation_Report.md` Section 5. The previous n=5 figure (one image per attack type, with a methodology bug that scored a multi-face image through the liveness model) has been superseded by a disclosed-methodology n=76 attack / n=75 genuine sample (4 real staged attack captures × ~19 realistic variants each; 5 real genuine captures across 2 identities × ~15 variants each — full disclosure of what "expanded" means in Section 5.1 of the Evaluation Report).

**At the deployed threshold (0.90):**
| Metric | Value |
|---|---|
| APCER (attacks wrongly accepted) | **46.05%** (35/76) — worse than the old 40%, not better |
| BPCER (genuine wrongly rejected) | **0.00%** (0/75) |
| ACER | **0.230** |

**Per-attack-type breakdown** — the aggregate number hides a very uneven picture:
| Attack Type | Miss Rate | Assessment |
|---|---|---|
| Printed Photo | 5.3% (1/19) | Reliably caught |
| Screen Replay (Phone) | 5.3% (1/19) | Reliably caught |
| Screen Replay (Laptop) | **73.7%** (14/19) | **Real, confirmed weakness** |
| Frozen Frame | **100%** (19/19) | Architecturally expected — this attack type belongs to active liveness, not passive (see brief's own attack table) |

A threshold-tradeoff sweep (Evaluation Report Section 5.1.2) shows raising the deployed threshold to 0.95–0.96 is a **free improvement** in this sample (BPCER stays at 0%, APCER drops ~8-9 points), but no threshold fully closes the screen-replay-laptop gap without a real, rising BPCER cost. **This report does not change the deployed threshold** — that decision is left to the project owner with this evidence in hand.

## 4. Limitations and Scope Decisions (stated plainly, not buried)

**rPPG (physiological liveness) — DEFERRED.** Implemented as an offline evaluation module (`src/rppg.py`, FFT-based pulse detection from forehead green-channel intensity) but not wired into the live registration/verification pipeline. *Why:* multi-frame buffering complexity — the live UI operates on a per-tick single-frame polling loop, whereas rPPG needs a stable, motion-free 10-15 second continuous capture window, which doesn't fit the existing interaction model without a larger UI redesign. Source: `docs/scope_decision_worksheet.md` Section 2.

**Active liveness implements 2 challenge types (blink, head-turn), not a larger set.** Blink detection (Eye Aspect Ratio) and head-turn detection (solvePnP-derived yaw) were chosen because they reuse infrastructure the pipeline already needs elsewhere — EAR-adjacent landmark geometry and solvePnP pose estimation are both already load-bearing for quality/pose checks — rather than requiring wholly separate detection infrastructure (e.g., smile or mouth-open detection) within the project's time budget. **This project's own attack testing (Section 3.2 above) directly confirms a consequence of this scope**: recorded-gesture attacks can bypass landmark-based active liveness. Tested directly against the real `run_blink_challenge()` function with a semi-synthetic replayed-blink video: **`status: 'pass'`, `min_ear_observed: 0.24`** — the replayed blink pattern was accepted. `cv2.VideoCapture` cannot distinguish a live camera from a replayed file, and the algorithm only ever evaluates per-frame landmark geometry, which a replay reproduces identically to a live feed. This was already a named, expected limitation in the Approach & Design Document; it is now confirmed with reproducible code-level evidence rather than left theoretical. Source: `data/Evaluation_Report.md` Section 5.2.

**Occlusion detection is a landmark-visibility approximation, not a trained classifier.** `check_occlusion()` flags possible occlusion using MediaPipe's per-landmark visibility/confidence score and local patch texture variance around the eyes/nose/mouth — a scoped-down proxy, explicitly documented as such in the Approach & Design Document, "due to time constraints." **What it can't distinguish**: it cannot tell *what* is occluding the face (mask vs. hand vs. hair vs. dark glasses) or reliably distinguish partial occlusion from certain lighting conditions that also depress local landmark confidence — it is a texture/confidence proxy for occlusion, not semantic object recognition. Additionally, `score_occlusion()` (the *weighted composite* sub-score used in the live quality gate) reads only BlazeFace's raw detection confidence, not the separate patch-variance "flat texture" reasoning `check_occlusion()`'s own binary status uses — a real architectural gap surfaced during the previous verification pass (see prior session's Part 1 fix in `app/streamlit_app.py`'s `_live_quality_failure_reason()`).

**Demographic bias — CONFIRMED, UNMITIGATED.** `day36_38_bias_testing.py` was run against 80 real CFP images across skin tone/gender/age subgroups (24-40 images per subgroup). Real, measured gaps:
- Quality pass rate: **Female 20.0%** (8/40) vs. **Male 42.5%** (17/40)
- Passive liveness pass rate: **Senior 25.0%** (6/24) vs. **Middle-aged 46.2%** (12/26)
- Skin tone: smaller but present gap — Dark 26.9% vs. Light 35.7% quality pass rate

Sample sizes are large enough to treat as a real signal, not large enough for regulatory-grade certainty. **No mitigation (rebalancing, per-subgroup threshold adjustment, retraining) has been attempted.** This is disclosed here explicitly, not left implicit in a script's console output. Source: `data/Evaluation_Report.md` Section 6, item 3.

**Multi-Angle Enrollment — SIMPLIFIED from the original three-angle design.** Registration now captures a single front-facing template instead of front/left/right. *Why:* the 3-step pose-gated capture flow was glitching in practice (getting stuck between front and left, never reaching right); `duplicate_check.py` already only ever compared front templates by design; and for a frontal live verification query, best-of-three matching resolved via the front template almost every time anyway, since cross-angle matching (EER 27.06%) is far weaker than frontal-frontal matching (EER 3.19%) — left/right templates were not meaningfully contributing to verification accuracy. Source: `docs/scope_decision_worksheet.md` Section 2.

**Known intermittent WebRTC connection hiccup — environmental, not an app bug.** Reproduced 3 times: the browser's WebRTC connection (`ctx.state.playing`) intermittently drops for 20-32 seconds, then self-recovers, typically 30-90 seconds into a session. Root-caused as far as the evidence allows: no exception or ICE/connection-state log line during the stall, no Windows Defender/System event log entry in the exact window, `aiortc`/`streamlit-webrtc` both current (not a known-buggy stale version) — most likely an aiortc peer-connection ICE consent-freshness/keepalive characteristic, self-healing without app intervention. **Status: known limitation, not chased further.** Practical mitigation for live demos: keep continuous camera segments under ~30 seconds, or be ready for one hard cut/retry. Source: `docs/scope_decision_worksheet.md` Section 3.

## 5. Registration Quality Checks Gap (closed this pass)

The brief's Phase 2 Section 3 lists four registration image-quality checks: brightness, contrast, blur, resolution. Brightness and blur existed; **contrast and resolution did not exist anywhere in the codebase** — confirmed by direct grep before writing any code. Both have now been added:
- `check_contrast()` (std of grayscale intensity, `CONTRAST_MIN = 30`, calibrated against real genuine captures measuring std 85-93 vs. synthetic wash-outs measuring 13-27)
- `check_resolution()` (face bounding-box width in pixels, `MIN_FACE_WIDTH_PX = 100`, calibrated against real genuine captures measuring 207-253px at the app's negotiated 640x360 resolution)

Both are wired into the shared `compute_quality_score()` composite (weights 0.05 each), the post-capture correction card (`explain_quality_failure()`), and the live per-tick guide message dictionary. Full detail and calibration reasoning: `data/Evaluation_Report.md` Section 7.

## 7. Learning Outcomes

Mapped against the brief's Expected Learning Outcomes list — computer vision, face recognition, liveness detection, biometric authentication, API development, performance evaluation — grounded in what this specific project actually required, not generic claims:

- **Computer Vision**: MediaPipe face detection and 468-point landmark geometry (with specific, confirmed-by-index landmark usage — nose tip [1], chin [152], eye corners [33, 263] for solvePnP; a separate 6-point-per-eye set for EAR); OpenCV `solvePnP` for real yaw/pitch/roll angle recovery from 2D landmarks against a generic 3D face model; classical statistical image-quality proxies (Laplacian-variance blur, mean-intensity brightness, std-of-intensity contrast) chosen deliberately over a trained model, informed by literature showing lightweight non-neural quality scoring is a legitimate, not underpowered, choice.
- **Face Recognition**: ArcFace embeddings via DeepFace, cosine-similarity matching, and — critically — the difference between a threshold chosen at the mathematically "optimal" EER point versus one chosen deliberately off that point for a security-first tradeoff (Section 3.1), including showing that tradeoff numerically rather than asserting it.
- **Liveness Detection**: a three-layer design (passive pretrained model, physiological rPPG, active challenge-response) motivated directly by published research showing single-method liveness systems are foolable; and, concretely, this project's own testing (Section 3.2, Section 4) demonstrating *why* that layering matters — the passive layer alone misses nearly half of a realistic attack sample at the deployed threshold, and the active layer alone is confirmed bypassable by a replayed recording.
- **Biometric Authentication**: end-to-end registration/verification with consent gating, duplicate-detection before enrollment, encryption at rest (Fernet AES-128), and GDPR/BIPA-oriented soft/hard deletion — implemented as production concerns, not afterthoughts, and each independently pytest-covered (Section 6).
- **API Development**: a FastAPI backend (`/register`, `/verify`) with API-key auth and a sliding-window rate limiter, deliberately kept separate from the orchestration logic in `pipeline.py` so the same pipeline is reachable from both the API and the Streamlit UI without duplication.
- **Performance Evaluation**: the field's actual standard metrics (APCER/BPCER/ACER, EER/ROC/AUC, HTER) instead of one invented "accuracy" number, applied consistently across matching (Section 3.1) and liveness (Section 3.2) — and, this pass specifically, the discipline of re-measuring a suspiciously small sample (n=5) rather than trusting it, disclosing that the larger sample came out *worse*, and showing a threshold tradeoff analysis rather than silently tuning a number to look better.
