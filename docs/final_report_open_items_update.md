# Replacement Text — "What Is Still Open or Needs More Work"

**This is plain markdown, not an edit to `Final_Report_Full.docx`.** That file gets updated by hand afterward using this text. One paragraph per original bullet, in the same order, reflecting what actually changed across the 4-phase stability/security pass this update closes out. Full supporting detail for every claim below lives in `docs/final_confirmation_report.md`, `data/Evaluation_Report.md`, and `docs/scope_decision_worksheet.md` — this document is the short, client-facing version.

---

**Screen-replay liveness gap.** The number this report previously led with — that a face replayed from a laptop screen is missed "a large share of the time" (73.7%) — measured something the live application doesn't actually use to make its decision, and has been corrected. Re-measured against the real, deployed decision logic: laptop-screen-replay is actually missed only about 5.3% of the time, not 73.7%. But the corrected investigation surfaced a different, previously-invisible gap in the same area: phone-screen-replay was being missed about 63.2% of the time. A new, lightweight supplementary check has been added specifically to close that gap, and it now measures 0% missed in the same test set, with no new false rejections of genuine users. This new check is calibrated on a small real sample — two real screen-replay photographs — and has not yet been validated against independently re-staged real attacks using different physical screens, lighting, and distances. A concrete plan for that follow-up capture work exists (`docs/screen_replay_capture_checklist.md`) but requires a person physically holding a screen up to a camera, which could not be done as part of this pass.

**Active-liveness bypass.** Still an open, disclosed limitation by design, not an oversight — and now backed by direct evidence rather than a theoretical concern alone. A controlled test confirmed that a replayed or synthetically-spliced blink can successfully pass the system's active-liveness challenge when its timing lines up favorably with the camera's capture rate. This is exactly why the system is built to layer multiple independent checks (passive liveness, active liveness, a physiological pulse-pattern check, and now the new screen-surface check above) rather than relying on any single one — no fix to the active-liveness layer itself is planned within this delivery.

**Per-tick response time.** Previously described qualitatively; now backed by real measurement. Across live test sessions, a typical check-to-check interval measured about 0.66 seconds, with slower moments occasionally reaching 2-3 seconds and one rare case taking about 14 seconds (traced to a one-time model-loading cost at the very start of a session, not a recurring slowdown). The system's built-in timeout windows — how long it waits for a gesture or a pulse reading before giving up — were checked against these real numbers and found to have comfortable margin; nothing needed to be changed, and nothing was changed just to look busy.

**Stability pass.** The specific crash found and fixed during the Layer 2/3 wiring work (a Streamlit-internals interaction on a genuine failed verification) now has a dedicated automated test guarding against it recurring, not just a one-time manual fix. Real-world timing tuning — how long feels right to wait for a gesture or a pulse reading before giving up — is still an open item requiring a live human tester's feedback across real verification and enrollment attempts; this cannot be closed out by automated testing alone and has not been attempted here.

**Fairness.** Measured gaps across gender, age, and skin tone remain real and unmitigated, as originally disclosed — that is a deliberate scope decision, not something overlooked. What's new this pass is *why*: for the skin-tone gap specifically, the driving factor is the system's brightness measurement — images of people with darker skin measured lower average brightness in testing, a well-documented pattern since darker skin reflects less light back to a camera, pushing those images closer to the system's minimum-brightness cutoff more often. The gender gap has a different, unrelated cause — a sharpness/focus measurement, not brightness — and its underlying reason has not yet been identified. No correction has been applied for either gap; both remain disclosed, open findings for the client to weigh before wider deployment.

**WebRTC connection hiccup.** Two distinct things are true here now. First, a real, separate application bug was found and fixed this pass: previously, if the camera connection dropped, the interface could get stuck showing stale information indefinitely, even after the connection quietly recovered on its own — it now checks again automatically and shows a clear "reconnecting" message instead of implying the user did something wrong. Second, the original mitigation attempt (a tolerance adjustment to the underlying connection library) still has not been confirmed effective against the original hiccup in real-world conditions — automated re-testing this pass could not cleanly reproduce the original phenomenon to validate it either way, so this remains an open item pending a real camera/browser test by a person, the same way the original issue was first found.

**Demo video.** Still not recorded — this remains the one item in the original brief that requires a person on camera and cannot be completed as part of this pass. What has changed: the recording script and shot list have been fully updated to match the current interface, including the live pass/fail checklist, the active-liveness gesture step, and the pulse-pattern check, none of which existed when the script was last written — recording against the old script would no longer match what's on screen. A step-by-step recording checklist is ready to hand to whoever records it.

**Final confirmation pass.** This document, together with `docs/final_confirmation_report.md`, is that pass — a fresh run of the full automated test suite and every evaluation script against the current, fully-updated system, confirming what's genuinely fixed, what's deliberately left open by design, and what still needs a human to close out.
